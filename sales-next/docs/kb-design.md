# 企業銷售知識庫 UX 呈現模式研究與設計建議

## 研究依據（成熟產品案例）

- **Guru**：以「卡片（Card）」為核心單位，卡片可加 Collection／Board 分類、標籤、到期覆核；瀏覽器擴充套件能在 Salesforce/Zendesk 等情境中依上下文主動推薦卡片。缺點：資料夾與雙向連結多了之後「folders and linking cards can feel clunky」，使用者最後把它當搜尋引擎用，而不是靠瀏覽逛。
- **Highspot**：用 SmartPages（依買家角色/產業/銷售階段策展的內容集合）+ Spots（分類容器），AI 自動打標籤、依情境（產業、角色、階段）推內容，走「Pinterest/iTunes 式」瀏覽體驗，而非純資料夾樹。
- **Gong**：Call Library 讓 AI 自動生成 Call Summary（highlights、next steps、action items），並可依教練情境策展「best-of」通話集；但使用者反映常常要在一堆 call cards 裡「scroll 尋找細節」，AI 產出內容多、"now what" 仍要人來判斷——這是純列表式呈現的通病。
- **Circleback**：把會議記錄自動做 Topic Segmentation（一場會議依討論主題切成多段，如「Website Redesign」「Budget Review」）與自動分類標籤（decisions／customer feedback／technical issues），並保留「連結回原始討論」的溯源，是最貼近本專案場景的案例。
- **Notion vs Obsidian（心智圖/圖譜）**：Obsidian 的 Graph View 適合「個人深度思考、探索性連結」的心智模型，但學習成本高、對「找答案」這種目標導向任務並不直接更快；Notion／Guru 這類「卡片 + 分類 + 搜尋」的組合更適合團隊協作與快速上手。NN/g 對 Card Sorting 的研究也指出：分類卡片式的資訊架構的核心價值是貼合使用者的「心智模型」與可尋性（findability），而純圖譜/心智圖對目標明確的查找任務（"這個異議怎麼回"）並沒有優勢，反而增加認知負擔。

結論：業界目前沒有一家嚴肅的 sales enablement 產品把心智圖／白板當作主要呈現層——心智圖類工具（Obsidian graph、Heptabase）定位始終是「探索與思考」，不是「隨手查找已知答案」。而「隨手查找」正是業務在會議前 5 分鐘、在客戶面前臨時查話術時的真實需求。

## 1. 推薦呈現模式與理由

**推薦：分類卡片式知識庫（Card + Category Grid），以 Guru/Highspot 的「Collection → Card」模型為骨架，疊加 Circleback 式的「主題自動切片＋來源溯源」，而非心智圖／白板。**

理由（對照四個考量）：

1. **黑客松 demo 的 wow 感**：wow 感不需要靠心智圖的視覺複雜度來製造，而是靠「一場會議講完 → 幾秒鐘後知識庫自動長出好幾張分類好的卡片，點進去還能看到是哪句話講的」這個「自動化+溯源」的動作本身就有戲劇性，且用網格/卡片呈現遠比拖拽心智圖節點更容易在 2.5 分鐘內講清楚、操作流暢不出錯。心智圖類 demo 風險高（連線亂、節點重疊、evaluators 看不懂結構）。
2. **AI 自動生成內容要能被瀏覽與信任**：卡片天然適合放「信心度／來源會議／更新時間」等中繼資料做信任訊號；心智圖節點空間有限，很難優雅塞入這些欄位，也難以做「未經確認」的視覺警示。
3. **業務日常真的會用**：業務要查東西時的心智模式是「我要找『競品比較』或『這句異議怎麼回』」，這是目標導向查找（goal-directed），對應 NN/g card sorting 研究裡「分類+搜尋」优於「探索圖譜」的場景。心智圖更適合沒有明確目的的探索，不是業務的日常。
4. **可維護性/工程成本**：卡片網格 + 分類 + 篩選是成熟、風險低的 UI pattern，一天內可做出高完成度的 demo；心智圖/白板（力導向圖、拖拽、縮放）在黑客松時間內容易做得半殘，反而拉低觀感。

折衷建議：不用「取代」而用「疊加」——分類卡片是主頁面，未來可選配一個「知識圖譜」次要視圖（例如點卡片後顯示『相關知識』的小型局部關聯圖，而非整庫心智圖），作為加分項而非主結構。

## 2. 頁面資訊架構

### 2.1 頂層分類（可依業務語意調整，建議 5–7 類，避免過多）

- **產業知識 Industry Insights**（客戶產業背景、痛點、法規趨勢）
- **競品比較 Competitive Intel**（對手優劣、battlecard、差異化話術）
- **客戶常見異議 Objection Handling**（異議 + 建議回應）
- **成功案例與話術 Case Studies & Talk Tracks**（成交故事、可複用話術）
- **產品/方案知識 Product & Offering**（產品細節、定價邏輯、常見問答）
- **客戶檔案 Account Notes**（依客戶/公司彙整，跨會議的持續累積資訊）
- （可選）**待確認 / 新出爐 Needs Review**（AI 剛生成、信心度低或尚未被人工確認的卡片，作為品質守門的收件匣）

分類方式：AI 產生卡片時自動打「主分類 + 次要標籤（產業別、客戶名、商機階段）」，允許同一張卡出現在多個篩選維度（分類是主導覽，標籤是篩選器），避免 Guru 那種「資料夾定死、卡片無法多重歸屬」的僵化問題。

### 2.2 每張知識卡片的欄位

| 欄位 | 說明 |
|---|---|
| 標題 Title | AI 生成，簡短動作/結論式（如「客戶常問：為何比競品貴」） |
| 摘要 Summary | 2–3 句 AI 摘要，卡片正面直接可讀完 |
| 分類 + 標籤 | 主分類 1 個、標籤多個（產業/客戶/商機階段） |
| 信心度 Confidence | 高/中/低，或百分比；AI 對此知識彙整正確性的自評，低信心加視覺警示（如黃色邊框） |
| 來源會議 Source Meeting(s) | 卡片可能彙整自多場會議，需列出每場會議名稱/日期/與會人，可多筆 |
| 更新時間 Last Updated | 最近一次被新會議內容補充/修正的時間 |
| 使用/被引用次數 Usage Count（可選加分項） | 這張卡片被查看/引用的次數，反映其熱門/有用程度 |
| 狀態 Status | 待確認 / 已採用 / 已過時（人工可標記） |
| 負責人/採用者 Owner（可選） | 若允許人工編輯或認領維護 |

卡片展開（點擊後）需顯示：
- 完整內容（不只是摘要，含 AI 整理的細節、建議話術全文）
- 溯源區塊：逐一列出來源會議，每筆可展開看「該段逐字稿摘錄」+ 一鍵跳轉到原始會議記錄的對應時間戳（若逐字稿有時間軸）
- 相關知識（同標籤/同客戶的其他卡片，推薦 3–5 張）
- 編輯/確認/標記過時等人工治理按鈕

## 3. 互動細節

- **搜尋**：頂部常駐全文搜尋框，同時搜標題/摘要/內容/標籤；支援關鍵字高亮，回傳仍是卡片網格。
- **篩選**：左側或頂部篩選列——依分類（單選 tab）、標籤（多選 chips：產業/客戶/商機階段）、信心度、時間範圍（近 7 天新增等）。篩選是「疊加」而非取代搜尋，可與搜尋並用。
- **排序**：預設「最近更新」，可切換「最常引用」「信心度」。
- **卡片點擊行為**：點擊卡片展開為右側 Drawer 或跳轉詳情頁（建議 demo 用 Drawer，動畫流暢、不離開列表上下文），展開後看到第 2 節列的完整內容 + 溯源。
- **溯源顯示**：這是信任感的關鍵，設計上要「一鍵可查」而非藏兩層——卡片正面就露出「來自 3 場會議」小標籤，展開後每場會議是一個可點的膠囊/連結，點了就跳到那場會議的摘要或逐字稿片段，理想上高亮那一句原話。這對應 Circleback「連結回原始討論」與 Gong call summary 的模式。
- **新卡片出現的動效**：demo 時建議做「知識庫即時生長」效果——上傳/處理完一場會議後，新卡片以淡入或輕微彈跳方式加到對應分類，配合角落 toast「新增了 4 張知識卡片」，這是最容易做出 wow 感、成本又低的細節。
- **低信心/待審卡片**：用不同視覺樣式（虛線邊框或黃色標籤「AI 待確認」），並集中在「待確認」分類，避免使用者對低品質內容產生誤信任。

## 4. Chat 問答的定位建議

Chat 不應被砍掉，而是重新定位為「知識庫之上的問答層」，兩者並存、互相導流：

- **知識庫（卡片瀏覽）= 系統一：主動探索與信任建立**。業務想「逛」某個主題、想確認某條資訊來源、想在會議前快速掃過某產業的所有相關卡片時用。這是「人瀏覽系統」。
- **Chat = 系統二：目標明確的即時提問**。業務在客戶面前臨時需要一個答案（「這客戶之前提过的異議是什麼」），用自然語言问一句比自己篩選分類更快。這是「系統回答人」。
- **串接設計**：
  - Chat 回答時，答案下方要附上引用的知識卡片（可點擊的小卡片摘要），既提高可信度，也把使用者導回知識庫瀏覽，形成雙向流動——這正是 Guru 卡片 + 對話介面成功案例的模式。
  - 知識庫頁面保留一個常駐的小型 Chat 入口（右下角浮動或頂部搜尋框旁「問 AI」按鈕），讓「搜尋找不到就直接問」成為自然的 fallback，而不是兩套獨立系統。
  - 兩者共用同一個信任機制：Chat 的回答也標示信心度與來源會議，與卡片一致，使用者不會覺得換了一套邏輯。

**Demo 敘事建議**：先展示知識庫網格（分門別類、一目了然）建立「這是真知識庫」的第一印象 → 點開一張卡看到溯源會議（建立信任）→ 上傳/播放一場新會議，卡片即時生長（wow）→ 最後用 Chat 問一句複合性問題，答案引用剛才看到的卡片，首尾呼應，證明瀏覽與問答是同一套資料的兩種入口。
